# アーキテクチャの判断記録

## 採用する境界

フロントエンドは静的ファイルとして配信し、API は単一のデプロイ単位にします。データは DynamoDB の 1 テーブルから始め、アクセスパターンが固まる前にテーブルを分割しません。

この構成では、画面の変更が API のデプロイを必ずしも必要とせず、API の障害が静的コンテンツの配信を止めません。一方で、画面と API は同じリポジトリで変更できるため、小規模開発での横断的な変更も追いやすくなります。

## 意図的にまだ入れないもの

- Kubernetes: 常時運用、クラスタ更新、ネットワーク設計の負担が先に増えるためです。
- 複数 API サービス: 障害分離よりも、認証・観測・デプロイ経路の重複が先に増えるためです。
- VPC: この最小構成のマネージドサービスだけでは、最初から必要になりません。
- 常時稼働データベース: アクセス量が不明な初期段階では、容量計画と保守作業を避けます。

## 境界を増やす条件

非同期化は「リクエスト内で完了を待てない処理」が出た時点で追加します。サービス分割は「別々にデプロイしなければ変更を安全に出せない」「権限や障害範囲を明確に分ける必要がある」のどちらかを、計測や運用記録で説明できる時点で判断します。
